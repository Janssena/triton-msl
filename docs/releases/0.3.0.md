# triton-msl 0.3.0

[Project](https://github.com/bledden/triton-msl) · [Usage](https://github.com/bledden/triton-msl/blob/main/docs/USAGE.md) · [Changelog](https://github.com/bledden/triton-msl/blob/main/CHANGELOG.md)

0.3.0 fixes kernels that could return incorrect results and expands attention and
matmul support. It also adds validation costs: some workloads take longer to start
and run. This guide summarizes what changes for users and where limitations remain.

See [GitHub releases](https://github.com/bledden/triton-msl/releases) for published
artifacts and their hashes.

## What improves

- **Matmul:** grouped and flat-grid kernels preserve the source's tile mapping.
  Bounded K-loop scaling and column-bias epilogues work, including fp16/bf16
  storage with fp32 arithmetic and supported rectangular tiles.
- **Attention:** more separate-query/key-length, single-query decode,
  bias-without-LSE, narrow-storage and larger-tile cases work. This includes the
  bounded workloads discussed in PR #7 and issue #11's matmul epilogue.
- **Correctness:** repairs cover broadcast indexing, shared-memory reuse races,
  reduction output offsets, integer address widths, partial-K loads and
  incorrectly selected specialized kernels.
- **Device assertions:** supported retained assertions stop guarded work and raise
  a host-visible error. Unsupported forms refuse rather than silently disappearing.
- **Packaging:** native CPU helpers accelerate validation and argument preparation;
  a Python fallback remains available.

Support is source-, dtype- and layout-specific, not a promise that every combination
works. See the [capability register](https://github.com/bledden/triton-msl/blob/main/docs/CAPABILITY_AND_REFUSAL_CENSUS.md)
for the exact recovered shapes and remaining refusals.

## Performance tradeoffs

Measurements use one M4 Max. Native and pure-Python installations have separate
results and should not be treated as interchangeable.

The warm comparison against previous public main retains **13 native and 14 pure
workloads more than 10% slower**, out of 18 comparable rows. These are synchronized
request latencies, not isolated GPU timings or predictions for every model.
Examples from the native run:

| Workload | Added time per request | Change |
|---|---:|---:|
| Vector add | 25.9 µs | +19.84% |
| Compiled MLP | 39.0 µs across two launches | +13.09% |
| GPT-2 small | 728.4 µs across 43 launches | +21.27% |

KDA prefill has a separate **10.16%** latency alert; paired blocks ranged from
7.21% to 13.13% longer. Wrong or refusing baseline kernels receive no speed ratio.
The varlen improvement uses a different execution route, not a same-route speedup.
These costs remain optimization opportunities, not proven lower bounds.

### Cold specialization

Single observations on the formatted candidate:

| Workload | Previous main | Native 0.3.0 | Pure 0.3.0 |
|---|---:|---:|---:|
| Add | 0.629 s | 9.480 s | 9.586 s |
| Compiled MLP | 0.861 s | 10.024 s | 10.053 s |
| GPT-2 small | 2.810 s | 5.130 s | 5.174 s |

These time the first synchronized specialization call, including compilation and
live validation—not imports, model construction or whole-application startup.
MLP and then GPT-2 shared a worker, so GPT-2 is not a fresh-interpreter measurement.
Identity hashing and discovery contribute substantial cold work. A persistent
manifest cache was investigated but not implemented; no new cache switch ships.

### FlashAttention

On the tested current software stack, the native wheel beats PyTorch MPS SDPA on
all **36 dense-attention medians**, but takes **23–44% longer than MLX**
(0.69–0.82× its speed). At batch 2, eight heads, head dimension 128 and
1,024–4,096 tokens, fp16 full attention is **1.94–2.18× SDPA's speed** and fp16
causal is **2.72–3.70×**. The pure wheel wins 34/36 dense medians against SDPA;
some fp32 cases are near parity and results vary across timed blocks.

A separate same-stack comparison found 0.3.0 took **8–29% longer than previous
main** on the tested dense cases and **12–13% longer** on two MLA cases. Previous
main also trails current MLX. Two dense cases have timed blocks crossing parity.
The update contributes to the gap, but the entire change since the August blog
has not been attributed to individual causes or software versions.

For MLA, native full attention at 1,024/2,048 tokens measured 1.08×/1.42× the speed
of SDPA with already-joined inputs; the 512-token case lost. The 1.08× case has
blocks crossing parity. Comparisons that include input concatenation are separate.

The August near-parity claim against MLX is historical, not a current guarantee.
Other historical throughput figures have not been requalified for this release.
[Full performance tables and methodology](https://github.com/bledden/triton-msl/blob/main/docs/RELEASE_CANDIDATE_LIMITATIONS.md)
retain the individual workloads, block variation and earlier observations.

## Validation scope

| Check | Result |
|---|---|
| Project tests | 6,079 passed / 16 skipped |
| Upstream Triton conformance | 5,780 passed / 3,562 skipped; 9,342 test cases |
| Installed-wheel acceptance | 1,468 native / 252 pure passes; no failures or skips |
| M4 Max performance floors | Four passed; these do not clear relative regressions |

The correctness tests, installed acceptance, floors and cold subset ran on the
formatted release candidate. Full warm comparisons and cross-vendor measurements
were collected before that formatting pass and **were not rerun on the formatted
artifacts**. Formatting preserved the reviewed syntax and emitted-kernel corpus,
but that is bounded evidence, not a guarantee about every kernel. The
[detailed validation record](https://github.com/bledden/triton-msl/blob/main/docs/RELEASE_CANDIDATE_LIMITATIONS.md#evidence-and-remaining-limitations)
preserves the exact source and artifact provenance.

### NVIDIA and AMD portability

The tested sources run through Triton's CUDA and ROCm backends on those GPUs,
not through the Metal compiler. **All 11 named byte-parity checks pass** across
Metal, NVIDIA A40 and AMD MI300X. That does not establish universal byte parity.

Metal passes all 16 required numerical rows in both packaging modes. A40 and
MI300X each pass 14/16: two default-precision attention rows remain outside the
original accuracy tolerance. Separate versions requesting explicit IEEE dot
precision pass both rows on every backend with unchanged inputs and tolerances.
The default-precision failures remain failures.
[Portability results and reproduction instructions](https://github.com/bledden/triton-msl/blob/main/PORTABILITY.md).

## Important limits and options

- **Hardware and applications:** release validation used one M4 Max. Independent
  M1 testing remains best-effort. The reported full AlphaFold/trifast application
  has not been validated end-to-end.
- **Native versus Python:** the native wheel targets GIL-enabled CPython 3.14,
  macOS 15+ arm64. The Python fallback has different latency. Build/import-only
  checks on other interpreters are not equivalent to GPU runtime qualification.
- **Observation callbacks:** the native fast path checks unchanged state without
  replaying Python key, descriptor, metadata or associated audit callbacks.
  If those callbacks or their side effects matter to your application, set
  `TRITON_MSL_IDENTITY_FAST_PATH=0` to use the complete evaluator on every call.
  Supported changes made between calls remain detected. Both public-launch
  validations, argument/ABI checks, submission tracking and immediate assertion
  observation stay enabled. JIT and Inductor use different validation counts.
- **Half accumulation:** `TRITON_MSL_FA_HALF_ACCUM=1` is opt-in and off by default.
  Historical speed/error figures in its docstring were not validated for this
  release and are not universal error bounds. Default-float tests do not validate
  this mode; check your actual inputs and shapes.
- **Optional C++ route:** off by default and unaudited. Including its sources in
  the source archive does not validate or enable it.

See the [full limitations](https://github.com/bledden/triton-msl/blob/main/docs/RELEASE_CANDIDATE_LIMITATIONS.md)
for unsupported cases, namespace handling, native-helper assumptions and diagnostics.

## If you need to roll back

Prefer recreating your earlier lockfile environment. Otherwise, pin
`triton-msl==0.2.0` in a fresh environment, restart the interpreter and verify
the imported path and version. This also restores the known 0.2.0 correctness
defects described in the [changelog](https://github.com/bledden/triton-msl/blob/main/CHANGELOG.md);
it is not a safety-equivalent fallback. A package pin alone does not restore
your previous PyTorch/Triton/MLX stack, and a full downgrade workflow has not been tested.
